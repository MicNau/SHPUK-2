# API расчётов

Семь эндпоинтов: шесть по типам объектов и один совокупный. Все принимают
`POST` с телом в JSON и отвечают сметой материалов и работами.

```
POST /api/v1/calculate_terrace/
POST /api/v1/calculate_steps/
POST /api/v1/calculate_fence/
POST /api/v1/calculate_railing/
POST /api/v1/calculate_path/
POST /api/v1/calculate_furniture/
POST /api/v1/calculate_project/
```

По результату любого расчёта можно получить смету в PDF — отдельными
эндпоинтами, см. раздел «Смета в PDF».

Первые пять считают объект по нарисованной геометрии. Мебель стоит особняком:
она считается по составу изделий, без геометрии, — формат ответа при этом
общий. Проект считает несколько объектов сразу и при желании сводит их
материалы в одну смету, см. раздел «Проект».

Координаты и все габариты — в миллиметрах.

## Ответ

```json
{
  "materials": {
    "deckingBoard": {
      "productId": 196304,
      "name": "Террасная доска ДПК",
      "ruTag": "Террасная доска",
      "productUrl": "https://outdoor-mebel.ru",
      "dimension": "м пог",
      "pricePerDimension": 1250.0,
      "totalDimensionCount": 102.0,
      "totalCost": 127500.0
    }
  },
  "works": [
    {"name": "Монтаж террасной доски из ДПК", "cost": 26400.0}
  ]
}
```

`materials` — словарь позиций, ключ описывает роль материала в объекте.
Позиции, для которых не нашлось товара, в ответе отсутствуют — состав `materials`
у одного и того же типа объекта может отличаться от запроса к запросу.

`works` — работы с их стоимостью. Тарифы пока заданы в коде расчёта и из
каталога не приходят.

### Запас, единицы и нормализация

`totalDimensionCount` — это количество в единицах продажи, а не физическая
величина. К любой позиции сначала добавляется **запас 10%** — на раскрой, бой
и подгонку, — и только потом результат приводится к единицам продажи:

- **Длинномер** (`"dimension": "м пог"`) — погонные метры, кратные длине
  изделия. Сотня метров лаги длиной 3 метра превращается в 111: с запасом
  выходит 110 метров, а метраж набирается целыми лагами, вверх.
- **Упаковки** (`"dimension": "упаковка 20 шт"`) — число упаковок, вверх до
  целой. 217 подложек с запасом дают 12 упаковок по 20. Размер упаковки
  указан в самой строке единицы.
- **Штуки** (`"dimension": "шт"`) — количество изделий, тоже с запасом и вверх:
  370 кляймеров превращаются в 408.

Запас берётся от чистой потребности, поэтому пересчитать её обратно из ответа
нельзя — приходит уже итоговое количество к заказу. В проекте с объединёнными
материалами запас и округление берутся один раз от суммы всех объектов, а не
у каждого по отдельности.

Исключение — секции забора, секции оградки, столбы и калитки: это готовые
изделия под конкретное место, и они приходят ровно в том количестве, которое
встало по геометрии, без запаса.

## Выбор товаров

Каждый расчёт идёт от главного материала: его выбирает пользователь, а
остальные материалы подтягиваются по ссылкам из его характеристик — доска
знает свою лагу, лага знает свою подложку.

Идентификатор главного материала передаётся в запросе. Его можно не указывать
или прислать `null` — тогда берётся товар по умолчанию.

**Сейчас переданный идентификатор не читается: расчёт всегда идёт на товарах
по умолчанию.** Так сделано временно, пока в каталоге не заполнены
характеристики товаров — без них выбранный товар всё равно дал бы только имя и
цену, а параметры расчёта пришли бы от товара по умолчанию. Поле в запросе
можно передавать уже сейчас, оно просто ни на что не влияет.

Часть материалов необязательна. Если товара под такую роль нет, расчёт
проходит, а позиция просто не попадает в смету:

| Расчёт | Необязательные позиции |
|---|---|
| Терраса | стартовые кляймеры |
| Ступени | — |
| Забор | калитки |
| Оградка | — |
| Дорожка | — |

## Терраса

```json
{
  "vertices": [
    {"x": 0, "y": 0, "vertexType": "house"},
    {"x": 6000, "y": 0, "vertexType": "house"},
    {"x": 6000, "y": 4000, "vertexType": "free"},
    {"x": 0, "y": 4000, "vertexType": "free"}
  ],
  "doorDirection": "N",
  "deckingBoardProductId": 196304
}
```

`vertexType` — `house` у вершин, примыкающих к дому, иначе `free`. Ребро
считается домовым, только когда оба его конца `house`: от этого зависит
направление лаг и длина свободного периметра.

`doorDirection` — сторона света, куда выходит дверь: `N` и `S` кладут лаги
вертикально, `E` и `W` — горизонтально. Поле необязательное: без него
лаги ложатся вертикально. Направление работает там, где его не диктует
примыкание к дому.

Позиции сметы: `deckingBoard`, `halfStep`, `angleBracket`, `rubberSupports`,
`joist`, `deckingClip`, `screw`.

## Ступени

```json
{
  "vertices": [
    {"x": 0, "y": 0, "vertexType": "terrace"},
    {"x": 3000, "y": 0, "vertexType": "terrace"},
    {"x": 3000, "y": 900, "vertexType": "free"},
    {"x": 0, "y": 900, "vertexType": "free"}
  ],
  "height": 600,
  "stepProductId": null
}
```

`vertexType` — `terrace` у вершин, примыкающих к террасе, иначе `free`.
`height` — высота подъёма от земли до террасы.

Число ступеней и отступ по высоте общие на всю фигуру и выводятся из габаритов
ступени и подступенка. Геометрия, из которой ступени собрать нельзя — слишком
частые ступени, слишком узкая ступень, прямоугольник без примыкания к террасе,
неописанный стык, — это 400 с текстом, объясняющим причину.

Позиции сметы: `step`, `riser`, `joist`, `rubberSupports`, `angleBracket`,
`screw`, `facadeBoard`.

## Забор

```json
{
  "lines": [
    [{"x": 0, "y": 0}, {"x": 6000, "y": 0}, {"x": 6000, "y": 3000}]
  ],
  "gateCount": 1,
  "sectionProductId": null,
  "picketProductId": null
}
```

`lines` — ломаные, по которым идёт забор. Их несколько, потому что калитки
разрывают забор, и каждый кусок между разрывами считается отдельно.
`gateCount` — сколько калиток; в геометрии они не участвуют и идут в смету
в сборе.

Товаров у забора два. Секция задаёт геометрию и приводит за собой столб и
калитку: длина каждого отрезка делится на минимальное число секций, при
котором их ширина не превышает предельной, а столбы встают на границах
секций. Штакетник — наполнение, с секцией он не связан и передаётся своим
идентификатором.

Позиции сметы: `section`, `post`, `gate`, `picket`.

## Оградка

```json
{
  "lines": [
    [{"x": 0, "y": 0}, {"x": 4000, "y": 0}]
  ],
  "sectionProductId": null
}
```

Геометрия та же, что у забора, но считаются только секции: оградка продаётся
секциями, в них уже всё входит.

Позиции сметы: `section`.

## Дорожка

```json
{
  "vertices": [
    {"x": 0, "y": 0, "vertexType": "start"},
    {"x": 1200, "y": 0, "vertexType": "start"},
    {"x": 1200, "y": 5000, "vertexType": "free"},
    {"x": 0, "y": 5000, "vertexType": "free"}
  ],
  "deckingBoardProductId": null
}
```

Контур замкнутый. Опорная сторона помечена `vertexType: "start"` у обеих своих
вершин — это ширина дорожки, от неё идёт обход. Дорожка считается лентой: от
опорной стороны отходят две боковые стороны, и на каждом повороте у обеих
появляется по вершине. Если вершин на сторонах разное число, дорожка не лента
и разбить её нельзя — это 400.

Позиции сметы: `deckingBoard`, `joist`, `rubberSupports`, `deckingClip`,
`starterClip`, `screw`.

## Мебель

Единственный расчёт без геометрии: на вход приходят готовые изделия из
каталога и их количество.

```json
{
  "items": {"196435": 2, "196436": 1}
}
```

Ключ — идентификатор товара в каталоге, значение — количество. Товар должен
быть основным материалом, иначе 403.

Ответ такой же, как у остальных расчётов. Позиции ключуются идентификатором
товара — ролей, как у объектов с геометрией, у мебели нет.

```json
{
  "materials": {
    "196435": {
      "productId": 196435,
      "name": "Скамья садовая",
      "ruTag": "Мебель",
      "productUrl": "https://outdoor-mebel.ru",
      "dimension": "шт",
      "pricePerDimension": 12000.0,
      "totalDimensionCount": 2,
      "totalCost": 24000.0
    }
  },
  "works": []
}
```

Работы всегда приходят пустым списком: состав работ по сборке не определён.
Запас 10% к мебели не применяется — сколько изделий выбрали, столько и в смете.

Формат временный: раскрой материала и работы по сборке ещё не решены.

## Проект

Несколько объектов одним расчётом. У каждого объекта свой тип, своё имя и то
же тело, что ушло бы в его собственный эндпоинт.

```json
{
  "objects": [
    {
      "type": "terrace",
      "name": "Терраса у входа",
      "vertices": [
        {"x": 0, "y": 0, "vertexType": "house"},
        {"x": 6000, "y": 0, "vertexType": "house"},
        {"x": 6000, "y": 4000, "vertexType": "free"},
        {"x": 0, "y": 4000, "vertexType": "free"}
      ],
      "doorDirection": "N"
    },
    {
      "type": "path",
      "name": "Дорожка к калитке",
      "vertices": [
        {"x": 0, "y": 0, "vertexType": "start"},
        {"x": 1200, "y": 0, "vertexType": "start"},
        {"x": 1200, "y": 5000, "vertexType": "free"},
        {"x": 0, "y": 5000, "vertexType": "free"}
      ]
    }
  ],
  "mergeMaterials": true
}
```

`name` — имя объекта от пользователя. Наружу оно возвращается как есть и
показывается в смете в PDF; на расчёт не влияет.

Имя необязательно: его можно не передавать или прислать пустую строку. Тогда
в ответе придёт `"name": ""`, заголовком раздела в смете станет тип объекта
(«Терраса», «Дорожка»), а в тексте ошибки объект назовётся просто по номеру —
`Объект 2`. Имена не обязаны быть уникальными: одинаковые объекты остаются
отдельными позициями ответа в том порядке, в котором пришли.

`mergeMaterials` определяет форму ответа.

### Материалы объединены

При `"mergeMaterials": true` ответ такой же, как у одиночного расчёта, —
`{materials, works}`. Позиции ключуются **идентификатором товара**, а не
ролью: у террасы и дорожки под одной ролью могут стоять разные товары, а под
разными ролями — один и тот же.

```json
{
  "materials": {
    "196304": {
      "productId": 196304,
      "name": "Террасная доска ДПК",
      "ruTag": "Террасная доска",
      "productUrl": "https://outdoor-mebel.ru",
      "dimension": "м пог",
      "pricePerDimension": 1250.0,
      "totalDimensionCount": 138.0,
      "totalCost": 172500.0
    }
  },
  "works": [
    {"name": "Монтаж террасной доски из ДПК", "cost": 41200.0}
  ]
}
```

Складывается **чистая потребность**, а запас 10% и приведение к единицам
продажи берутся один раз от суммы. Поэтому объединённая смета дешевле, чем
сумма отдельных расчётов тех же объектов: три террасы дают один хвост лаги
вместо трёх. Пересчитать одно из другого нельзя.

Работы объединяются по названию: одинаковые складываются в одну строку.

### Материалы по объектам

При `"mergeMaterials": false` (или без этого поля) общей сметы нет — ответ
содержит только `objects`, по одному на каждый объект запроса, в том же
порядке. Внутри объекта смета обычная, с ролевыми ключами.

```json
{
  "objects": [
    {
      "type": "terrace",
      "name": "Терраса у входа",
      "materials": {"deckingBoard": {"...": "..."}},
      "works": [{"name": "Монтаж террасной доски из ДПК", "cost": 26400.0}]
    },
    {
      "type": "path",
      "name": "Дорожка к калитке",
      "materials": {"deckingBoard": {"...": "..."}},
      "works": [{"name": "Монтаж дорожки из ДПК", "cost": 14800.0}]
    }
  ]
}
```

Общей стоимости в ответе нет: складывается она на стороне клиента.

### Ошибки объектов

Ошибка любого объекта роняет весь расчёт — смета проекта без одного из
объектов не смета проекта. К тексту ошибки спереди приписывается, о каком
объекте речь: `Объект 2 «Дорожка к калитке»: Минимум 4 точки`. Статус ответа
тот же, что был бы у одиночного расчёта: 400 у геометрии, 404 у материалов.

Число объектов в проекте не ограничено, но расчёт синхронный: десяток тяжёлых
контуров считается заметное время.

## Смета в PDF

По любому расчёту можно получить смету в PDF. Собирается она фоновой задачей —
расчёт и вёрстка занимают время, — поэтому одним запросом файл не приходит:
задача ставится, потом опрашивается её состояние.

```
POST /api/v1/calculation_report/            запуск
GET  /api/v1/calculation_report/{taskId}/   состояние
GET  /api/v1/calculation_report/file/{name} файл
```

### Запуск

Тело — тип объекта и то же, что уходит в расчёт этого типа:

```json
{
  "type": "terrace",
  "vertices": [
    {"x": 0, "y": 0, "vertexType": "house"},
    {"x": 6000, "y": 0, "vertexType": "house"},
    {"x": 6000, "y": 4000, "vertexType": "free"},
    {"x": 0, "y": 4000, "vertexType": "free"}
  ],
  "doorDirection": "N"
}
```

`type` — `terrace`, `steps`, `fence`, `railing`, `path`, `furniture` или
`project`. У проекта тело такое же, как у расчёта: `objects` и
`mergeMaterials`. Ответ приходит сразу, со статусом 202:

```json
{"taskId": "11009a94-16aa-4374-96bd-bc401a97c8c8", "status": "pending"}
```

Неизвестный тип объекта и невалидный JSON дают 400. Ошибки геометрии и
подбора товаров на этом шаге не проверяются: расчёт идёт уже в задаче, и они
приходят её состоянием.

### Состояние

```json
{"status": "ready", "url": "/api/v1/calculation_report/file/terrace-b8d391780771.pdf"}
```

| `status` | Что значит |
|---|---|
| `pending` | задача в очереди или считается |
| `ready` | смета готова, рядом `url` файла |
| `failed` | расчёт не прошёл, рядом `error` с текстом |

В `failed` лежит та же ошибка, что вернул бы обычный расчёт — например,
`Ступени вышли бы слишком частыми: ...` или `Нечем закрыть позицию «лага»: ...`,
— так что показывать её можно напрямую.

Опрашивать состояние разумно раз в секунду: смета собирается за несколько
секунд, но задачи выполняются по две за раз и при очереди ждать придётся
дольше.

### Файл

По `url` из готового состояния отдаётся сам PDF, `Content-Type:
application/pdf`. Ссылка постоянная, файл лежит на сервере и повторным
запросом не пересобирается. Имя формируется задачей; чужое или несуществующее
имя даёт 404.

Содержимое сметы: шапка с логотипом, заголовок с типом объекта и датой,
параметры объекта, таблицы материалов и работ с итогами и оговорки о том, что
в расчёт заложено, а что в него не входит.

У проекта смета строится вокруг объектов и показывает их имена. С
объединёнными материалами это перечень «Состав проекта» — имя, тип и
параметры каждого объекта, — а следом общие таблицы материалов и работ. Без
объединения у каждого объекта свой раздел со своей таблицей и итогом, а
внизу — итог по проекту. Оговорки собираются по типам, вошедшим в проект.

## Ошибки

Тело ошибки — `{"error": "текст"}`. Тексты рассчитаны на показ пользователю:
они объясняют, что именно не сошлось, и не содержат внутренних терминов.
В фигурных скобках ниже — подставляемые значения.

### Общие для всех расчётов

| Код | Текст | Когда |
|---|---|---|
| 400 | `Невалидный JSON` | тело запроса не разбирается |
| 404 | `Продукт не найден` | передан идентификатор товара, которого нет в каталоге |
| 404 | `Нечем закрыть позицию «{материал}»: товар не выбран и товара по умолчанию нет` | обязательный материал не задан ни ссылкой, ни товаром по умолчанию |
| 404 | `Не найден товар, выбранный как {материал} (id {id})` | в характеристиках выбранного товара стоит ссылка на несуществующий товар |
| 404 | `У товара {id} ({материал}) не заполнены характеристики` | товар найден, но параметров расчёта у него нет |
| 404 | `У товара {id} не заполнены характеристики, а товара по умолчанию ({материал}) в каталоге нет` | то же про главный материал, когда подставить нечего |
| 500 | `Internal server error` | необработанная ошибка расчёта |

Все 404 про материалы — про наполнение каталога, а не про действия
пользователя: чинятся заведением товара или заполнением его характеристик.

### Терраса

| Текст | Когда |
|---|---|
| `Не переданы точки контура` | `vertices` пустой или отсутствует |
| `Минимум 3 точки` | точек меньше трёх |
| `Направление двери должно быть N, S, E или W` | `doorDirection` задан чем-то другим |

### Ступени

| Текст | Когда |
|---|---|
| `Не переданы точки контура` | `vertices` пустой или отсутствует |
| `Минимум 3 точки` | точек меньше трёх |
| `Не передана высота` | нет `height` |
| `Высота подъёма должна быть больше нуля` | `height` ноль или отрицательная |
| `Есть часть фигуры, не примыкающая к террасе ни одной стороной — ступеням неоткуда начинаться` | нарисованная область не касается террасы; вершины примыкания помечаются `terrace` |
| `Ступени вышли бы слишком частыми: фигуре нужно {n} ступеней, а по высоте {h} мм помещается не больше {k}` | глубина требует больше ступеней, чем позволяет высота: нужно уменьшить глубину или поднять высоту |
| `Ступень выходит шириной {w} мм при минимальной {m} мм: не хватает глубины` | ступеней много, а глубины на них не хватает |
| `Части фигуры пересекаются, и ступени в этом месте не стыкуются: они шли бы в одну сторону с разной шириной` | две области накладываются и требуют разной раскладки в одном месте |
| `Слишком сложная форма: части фигуры пересекаются не углом, ступени в этом месте не состыковать` | области пересекаются не внешним углом — такую форму расчёт не берёт |

Три последние ошибки — про форму: они означают, что фигуру надо перерисовать,
а не поменять параметры.

### Забор

| Текст | Когда |
|---|---|
| `Нужна хотя бы одна линия` | `lines` пустой или отсутствует |
| `Линия {n}: нужно минимум 2 точки` | в линии одна точка |
| `Линия {n}: нулевая длина` | все точки линии совпали |
| `Количество калиток не может быть меньше нуля` | отрицательный `gateCount` |

### Оградка

| Текст | Когда |
|---|---|
| `Нужна хотя бы одна линия` | `lines` пустой или отсутствует |
| `Линия {n}: нужно минимум 2 точки` | в линии одна точка |
| `Линия {n}: нулевая длина` | все точки линии совпали |

### Дорожка

| Текст | Когда |
|---|---|
| `Не переданы точки контура` | `vertices` пустой или отсутствует |
| `Минимум 4 точки` | точек меньше четырёх: у дорожки есть стартовая сторона и две боковые |
| `Не отмечена стартовая сторона — с неё начинается дорожка` | ни у одной пары соседних вершин нет `vertexType: "start"` |
| `Стартовая сторона не найдена в контуре` | сторона помечена, но её вершины не совпали с вершинами контура |
| `Форма не похожа на дорожку: {n} вершин в контуре, стороны не сопоставляются попарно` | нечётное число вершин: у боковых сторон разное число поворотов |

### Мебель

| Код | Текст | Когда |
|---|---|---|
| 400 | `Нужен словарь id товара и количества` | `items` пустой или не объект |
| 400 | `id и количество должны быть числами` | ключ или значение не приводятся к числу |
| 400 | `Количество для товара {id} должно быть больше нуля` | количество ноль или отрицательное |
| 404 | `Товары не найдены: {id, id}` | перечислены идентификаторы, которых нет в каталоге |
| 403 | `Не основные материалы: {id, id}` | перечислены товары, не помеченные основным материалом |

### Проект

| Текст | Когда |
|---|---|
| `Не переданы объекты проекта` | `objects` пустой или не список |
| `Объект {n}: нужен объект с типом и данными` | элемент `objects` не объект |
| `Объект {n} «{имя}»: неизвестный тип объекта: {тип}` | у объекта нет `type` или он не из списка типов |
| `Объект {n} «{имя}»: {ошибка расчёта}` | объект не посчитался: дальше идёт обычный текст ошибки его типа |

Имя в префиксе появляется, только если оно передано; без него — просто
`Объект {n}`.

Все ошибки в разделах по типам приходят со статусом 400, кроме мебели, где
статус указан отдельной колонкой, и ошибок объектов проекта, где статус
наследуется от расчёта объекта.

## Отладочный режим

Расчёт помимо сметы строит геометрию: прямоугольники покрытия, лаги, опоры,
полосы ступеней, секции. Наружу она не отдаётся — только смета и работы.

Отладочные страницы получают её, добавляя в тело запроса `"debug": true`:
тогда ответ содержит полный результат расчёта, а смета лежит в нём под ключом
`materials`. Состав отладочных полей у каждого типа свой и контрактом не
является — он может меняться вместе с алгоритмом.

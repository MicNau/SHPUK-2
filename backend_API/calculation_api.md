# API расчётов

Девять эндпоинтов: восемь по типам объектов и один совокупный. Все принимают
`POST` с телом в JSON и отвечают сметой материалов и работами.

```
POST /api/v1/calculate_terrace/
POST /api/v1/calculate_steps/
POST /api/v1/calculate_fence/
POST /api/v1/calculate_railing/
POST /api/v1/calculate_path/
POST /api/v1/calculate_facade/
POST /api/v1/calculate_furniture/
POST /api/v1/calculate_garden_beds/
POST /api/v1/calculate_project/
```

По результату любого расчёта можно получить смету в PDF — отдельными
эндпоинтами, см. раздел «Смета в PDF».

Первые шесть считают объект по нарисованной геометрии. Мебель и грядки стоят
особняком: они считаются по составу изделий, без геометрии, — формат ответа
при этом общий. Проект считает несколько объектов сразу и при желании сводит
их материалы в одну смету, см. раздел «Проект».

Координаты и все габариты — в миллиметрах.

## Ответ

```json
{
  "materials": {
    "deckingBoard": {
      "productId": 196304,
      "name": "Террасная доска ДПК",
      "ruTag": "Террасная доска",
      "productUrl": "https://outdoor-mebel.ru",
      "dimension": "м пог",
      "pricePerDimension": 1250.0,
      "totalDimensionCount": 102.0,
      "totalCost": 127500.0
    }
  },
  "works": [
    {
      "name": "Монтаж террасной доски из ДПК",
      "dimension": "м²",
      "pricePerDimension": 1100.0,
      "totalDimensionCount": 24.0,
      "cost": 26400.0
    }
  ]
}
```

`materials` — словарь позиций, ключ описывает роль материала в объекте. У
фасада ключ — идентификатор товара, см. раздел «Фасад».
Позиции, для которых не нашлось товара, в ответе отсутствуют — состав `materials`
у одного и того же типа объекта может отличаться от запроса к запросу. Не
приходят и позиции с нулевым количеством: заказывать нечего, поэтому строки
нет вовсе — например, калиток у забора, если их не поставили.

`works` — работы. Считаются так же, как материалы: единица измерения, тариф
за неё и объём, а `cost` — их произведение. Объём берётся из геометрии
объекта: у террасы, ступеней, дорожки и фасада это площадь в м², у забора и оградки —
длина в погонных метрах. `cost` был в ответе и раньше, остальные поля
добавлены рядом с ним.

Тарифы пока заданы в коде расчёта и из каталога не приходят.

Позиции `screw` больше нет ни в одном расчёте: саморезы из смет убраны.

### Запас, единицы и нормализация

`totalDimensionCount` — это количество в единицах продажи, а не физическая
величина: посчитанная потребность приводится к тому, чем товар продаётся.

- **Длинномер** (`"dimension": "м пог"`) — погонные метры, кратные длине
  изделия. Сотня метров лаги длиной 3 метра превращается в 102: метраж
  набирается целыми лагами, вверх.
- **Упаковки** (`"dimension": "упаковка 20 шт"`) — число упаковок, вверх до
  целой. 217 подложек дают 11 упаковок по 20. Размер упаковки указан в самой
  строке единицы.
- **Штуки** (`"dimension": "шт"`) — количество изделий, вверх до целого.

**Общий запас 10% больше не начисляется.** Раньше он добавлялся к любой
позиции до приведения к единицам продажи; теперь количество считается без
него — сколько встало по геометрии, столько и заказывается. Округление вверх
до целого изделия, упаковки или штуки осталось.

Запас на раскрой сохранился только там, где материал режут: **5% к террасной
доске, лаге, ступени, подступенку и фасадной доске**. Это не надбавка к смете,
а часть расчёта метража: длинномер кроится под размер, и обрезки в дело не
идут. Величина приходит из характеристики `waste_factor` товара, поэтому у
разных изделий может отличаться. Штакетник забора считается **без запаса**:
доска ставится целой, резать её незачем.

В проекте с объединёнными материалами округление берётся один раз от суммы
всех объектов, а не у каждого по отдельности.

Секции забора, калитки, столбы, а у оградки крышки-юбки и стаканы приходят
ровно в том количестве, которое встало по геометрии: это готовые изделия под
конкретное место, и округлять там нечего.

## Выбор товаров

Каждый расчёт идёт от главного материала: его выбирает пользователь, а
остальные материалы подтягиваются по ссылкам из его характеристик — доска
знает свою лагу, лага знает свою подложку.

Идентификатор главного материала передаётся в запросе. Его можно не указывать
или прислать `null` — тогда берётся товар по умолчанию.

Передавать нужно тот же составной `id`, что приходит в выдаче каталога:
товар вместе с кодом конфигурации. Расчёт разбирает его, разворачивает
конфигурацию и берёт характеристики именно выбранной комбинации вариантов —
у разных цветов и размеров одного товара они свои.

Товар каталога может не нести характеристик вовсе. Тогда параметры расчёта
приходят от товара по умолчанию, а от выбранного остаются имя и цена.

Цена позиции — цена выбранной конфигурации: если у неё своя цена, в смету
идёт она, иначе цена товара каталога. Это та же цена, что приходит в `prices`
выдачи каталога, см. «Цена конфигурации».

Часть материалов необязательна. Если товара под такую роль нет, расчёт
проходит, а позиция просто не попадает в смету:

| Расчёт | Необязательные позиции |
|---|---|
| Терраса | стартовые кляймеры |
| Ступени | — |
| Забор | калитки |
| Оградка | — |
| Дорожка | — |
| Фасад | — |

## Терраса

```json
{
  "vertices": [
    {"x": 0, "y": 0, "vertexType": "house"},
    {"x": 6000, "y": 0, "vertexType": "house"},
    {"x": 6000, "y": 4000, "vertexType": "free"},
    {"x": 0, "y": 4000, "vertexType": "free"}
  ],
  "doorDirection": "N",
  "deckingBoardProductId": 196304
}
```

`vertexType` — `house` у вершин, примыкающих к дому, иначе `free`. Ребро
считается домовым, только когда оба его конца `house`: от этого зависит
направление лаг и длина свободного периметра.

`doorDirection` — сторона света, куда выходит дверь: `N` и `S` кладут лаги
вертикально, `E` и `W` — горизонтально. Поле необязательное: без него
лаги ложатся вертикально. Направление работает там, где его не диктует
примыкание к дому.

Часть лаг двойная, и их метраж входит в позицию `joist` дважды: двойными
идут лаги на стыках досок и крайняя лага у каждого свободного края — на неё
опираются короткие поперечины, которые держат полуступень.

Позиции сметы: `deckingBoard`, `halfStep`, `angleBracket`, `rubberSupports`,
`joist`, `deckingClip`.

## Ступени

```json
{
  "vertices": [
    {"x": 0, "y": 0, "vertexType": "terrace"},
    {"x": 3000, "y": 0, "vertexType": "terrace"},
    {"x": 3000, "y": 900, "vertexType": "free"},
    {"x": 0, "y": 900, "vertexType": "free"}
  ],
  "height": 600,
  "stepProductId": null
}
```

`vertexType` — `terrace` у вершин, примыкающих к террасе, иначе `free`.
`height` — высота подъёма от земли до террасы.

Число ступеней и отступ по высоте общие на всю фигуру и выводятся из габаритов
ступени и подступенка. Геометрия, из которой ступени собрать нельзя — слишком
частые ступени, слишком узкая ступень, прямоугольник без примыкания к террасе,
неописанный стык, — это 400 с текстом, объясняющим причину.

Позиции сметы: `step`, `riser`, `joist`, `rubberSupports`, `angleBracket`,
`facadeBoard`.

## Забор

```json
{
  "lines": [
    [{"x": 0, "y": 0}, {"x": 6000, "y": 0}, {"x": 6000, "y": 3000}]
  ],
  "gateCount": 1,
  "sectionProductId": null,
  "picketProductId": null
}
```

`lines` — ломаные, по которым идёт забор. Их несколько, потому что калитки
разрывают забор, и каждый кусок между разрывами считается отдельно.
`gateCount` — сколько калиток; в геометрии они не участвуют и идут в смету
в сборе.

Товаров у забора два. Секция задаёт геометрию и приводит за собой столб и
калитку: длина каждого отрезка делится на минимальное число секций, при
котором их ширина не превышает предельной, а столбы встают на границах
секций. Штакетник — наполнение, с секцией он не связан и передаётся своим
идентификатором.

Столбы приходят штуками: столб покупается готовым изделием, и на каждый
столб забора уходит ровно один — по умолчанию длиной 2,5 м. Раньше эта
позиция считалась метражом, `dimension` у неё был `м пог`.

Позиции сметы: `section`, `post` (шт), `gate`, `picket`.

## Оградка

```json
{
  "lines": [
    [{"x": 0, "y": 0, "vertexType": "house"}, {"x": 4000, "y": 0}]
  ],
  "sectionProductId": null
}
```

Отрезок ломаной набирается секциями не шире предельной ширины (1200 мм):
любой остаток добавляет целую секцию, а ширина раскладывается по отрезку
поровну. Столбы стоят между секциями, поэтому **каждая ломаная начинается и
кончается столбом**, и столбов на ней на один больше, чем секций; на изломе
ломаной столб общий для двух отрезков.

### Примыкание к дому

`vertexType: "house"` у точки означает, что оградка примыкает там к стене:
столба на этом конце нет, оградка крепится к дому. Поле необязательное — без
него всё считается как раньше, и присылать его нужно только там, где
примыкание есть.

Отмечать можно **только концы ломаной**, первую и последнюю точку. Метка на
внутренней точке — ошибка (400), потому что в середине линии примыкание
ничего не значит: столб на изломе всё равно нужен.

У забора это поле пока не действует: там примыкания нет, и присланная метка
ничего не меняет.

### Ширина столба

Столб занимает место вдоль линии наравне с секцией, поэтому шаг разбиения —
это **ширина секции плюс ширина столба**. Ширина берётся из габаритов товара
столба (`dimensions.width`); если она не заполнена, столб считается точкой, и
разбиение получается прежним.

Отсюда и смысл примыкания: убрали столб — освободилось место под секции.
При секции 1000 мм и столбе 100 мм линия длиной 3,4 м даёт 3 секции и
4 столба, а с одним примыканием те же 3 секции занимают 3,3 м:

| Примыканий | Секций | Столбов | Длина линии |
|---|---|---|---|
| 0 | 3 | 4 | 3400 мм |
| 1 | 3 | 3 | 3300 мм |
| 2 | 3 | 2 | 3200 мм |

Число секций считается обратной формулой, с округлением вверх:

```
секций = ceil( (длина − (1 − примыканий) × ширина столба)
               / (ширина секции + ширина столба) )
```

После этого фактическая ширина секции раскладывается поровну по тому, что
осталось от линии за вычетом столбов, — так нарисованная длина сходится
точно. Если столбы занимают линию целиком и на секцию длины не остаётся,
расчёт отвечает 400.

В смету идут материалы, а не секции: секция задаёт только шаг разбиения и
собственной позицией в ответе не приходит. Часть норм привязана к секции,
часть — к столбу:

| Позиция | Ключ | Норма |
|---|---|---|
| Перила | `railingRail` | 2 м пог на секцию |
| Балясины | `baluster` | 4 шт (3 м пог) на секцию |
| Столбы оградки | `post` | 1 м пог на столб |
| Крепления перил | `railBracket` | 4 шт на секцию |
| Крепления балясин | `balusterBracket` | 8 шт на секцию |
| Крышки-юбки столбов | `postCap` | 1 шт на столб |
| Стаканы столбов | `postBase` | 1 шт на столб |

Позиции сметы: `railingRail`, `baluster`, `post`, `railBracket`,
`balusterBracket`, `postCap`, `postBase`.

Столб у оградки — та же роль `post`, что у забора: роль одна, а товар свой,
он выбирается по типу расчёта.

Столбы приходят метражом: на ограду уходит метр столба, и метраж в смете
ровно тот, что встал, без набора целыми столбами по их длине. Одиннадцать
столбов ограды — это 11 погонных метров в смете.

## Дорожка

```json
{
  "vertices": [
    {"x": 0, "y": 0, "vertexType": "start"},
    {"x": 1200, "y": 0, "vertexType": "start"},
    {"x": 1200, "y": 5000, "vertexType": "free"},
    {"x": 0, "y": 5000, "vertexType": "free"}
  ],
  "deckingBoardProductId": null
}
```

Контур замкнутый. Опорная сторона помечена `vertexType: "start"` у обеих своих
вершин — это ширина дорожки, от неё идёт обход. Дорожка считается лентой: от
опорной стороны отходят две боковые стороны, и на каждом повороте у обеих
появляется по вершине. Если вершин на сторонах разное число, дорожка не лента
и разбить её нельзя — это 400.

Позиции сметы: `deckingBoard`, `joist`, `rubberSupports`, `deckingClip`,
`starterClip`.

## Фасад

`POST /api/v1/calculate_facade/`

### Что отправить

Тело запроса — один ключ `pieces`: список участков обшивки на стенах дома.

```json
{
  "pieces": [
    {"wallId": 1, "productId": null,
     "vertices": [{"x": 0, "y": 0}, {"x": 2000, "y": 0}, {"x": 2000, "y": 2800}, {"x": 0, "y": 2800}]},
    {"wallId": 1, "productId": null,
     "vertices": [{"x": 3500, "y": 0}, {"x": 6000, "y": 0}, {"x": 6000, "y": 2800}, {"x": 3500, "y": 2800}]},
    {"wallId": 1, "productId": null,
     "vertices": [{"x": 2000, "y": 0}, {"x": 3500, "y": 0}, {"x": 3500, "y": 900}, {"x": 2000, "y": 900}]},
    {"wallId": 1, "productId": null,
     "vertices": [{"x": 2000, "y": 2100}, {"x": 3500, "y": 2100}, {"x": 3500, "y": 2800}, {"x": 2000, "y": 2800}]},
    {"wallId": 2, "productId": "196500",
     "vertices": [{"x": 0, "y": 0}, {"x": 4000, "y": 0}, {"x": 4000, "y": 2800}, {"x": 0, "y": 2800}]}
  ]
}
```

Здесь стена 1 шириной 6 м с окном 1,5×1,2 м, обойдённым четырьмя участками, и
глухая стена 2 шириной 4 м другой доской.

Поля участка:

| Поле | Тип | Обязательно | Что это |
|---|---|---|---|
| `wallId` | число или строка | да | Стена, на которой лежит участок. `1` и `"1"` — одна и та же стена |
| `productId` | составной `id` или `null` | нет | Фасадная доска участка из выдачи каталога; `null` или отсутствие — доска по умолчанию |
| `vertices` | массив `{x, y}` | да | Контур участка, минимум 3 точки, миллиметры |

Как задавать участки:

- **Координаты свои у каждой стены.** Начало — в любом удобном углу стены,
  `x` идёт вдоль стены, `y` — **вверх**. Одинаковые координаты на разных стенах —
  это разные участки, поэтому `wallId` обязателен.
- **Контур не замыкается повтором первой точки**, порядок обхода любой — по
  часовой или против.
- **Дырок в участке быть не может.** Окно или дверь обходится несколькими
  участками, как в примере: слева, справа, под и над проёмом. Участки одной
  стены и одной доски с общей стороной сами склеиваются в один кусок обшивки,
  так что резать можно как угодно.
- **Участки одной стены не накладываются** друг на друга, даже разными
  досками, — это 400. Касаться сторонами и вершинами можно.
- **Контур без самопересечений.** Наклонные стороны допустимы — фронтон,
  скат, мансарда.
- **Разные доски** — просто разный `productId` у участков. Сколько досок в
  одном запросе, не ограничено.

### Что придёт

Обычный ответ `{materials, works}`, одна смета на все стены и доски. Ключи
позиций — **идентификаторы товаров**, а не роли, как в объединённой смете
проекта: под «доской» может стоять несколько товаров. Одинаковые товары разных
досок — например, общая лага — складываются в одну строку. Что есть что,
видно по `ruTag`.

Пример — ответ на глухую стену 6×2,8 м с фронтоном высотой 1,7 м, доской по
умолчанию:

```json

    "-24": {"productId": -24, "name": "Доска фасадная ДПК для обшивки стен", "ruTag": "Фасадная доска",
            "productUrl": "https://outdoor-mebel.ru", "dimension": "м пог",
            "pricePerDimension": 630.0, "totalDimensionCount": 105.0, "totalCost": 66150.0},
    "-5":  {"productId": -5, "name": "Лага ДПК", "ruTag": "Лаги",
            "productUrl": "https://outdoor-mebel.ru", "dimension": "м пог",
            "pricePerDimension": 190.0, "totalDimensionCount": 66.0, "totalCost": 12540.0},
    "-25": {"productId": -25, "name": "Профиль стартовый фасадный", "ruTag": "Стартовый профиль",
            "productUrl": "https://outdoor-mebel.ru", "dimension": "м пог",
            "pricePerDimension": 583.0, "totalDimensionCount": 6.0, "totalCost": 3498.0},
    "-26": {"productId": -26, "name": "Уголок фасадный", "ruTag": "Уголки",
            "productUrl": "https://outdoor-mebel.ru", "dimension": "м пог",
            "pricePerDimension": 335.0, "totalDimensionCount": 15.0, "totalCost": 5025.0},
    "-9":  {"productId": -9, "name": "Кляймер рядовой", "ruTag": "Кляймеры",
            "productUrl": "https://outdoor-mebel.ru", "dimension": "шт",
            "pricePerDimension": 17.0, "totalDimensionCount": 482, "totalCost": 8194.0}
  },

```

В проекте фасад передаётся объектом `{"type": "facade", "name": "...", "pieces": [...]}`.
Ошибки — в разделе «Ошибки», подраздел «Фасад».

### Как считается

- **Лаги** идут поперёк доски: направление доски — характеристика товара.
  Шаг равномерный и не больше предельного (400 мм у доски по умолчанию), через
  каждую длину доски лага двойная. Там, где обшивка прерывается, прерывается и
  лага.
- **Стартовый профиль** — по низу фасада: по нижнему краю обшивки, под которым
  обшивки этой стены нет. **Уголок** — по всему остальному свободному краю,
  в том числе по верху окон и дверей. Где участок
  примыкает к участку другого материала, край не обрамляется. Лаги, профиль и
  уголок идут метражом без запаса. Стены между собой не связаны, поэтому на
  углу дома уголков два — по одному от каждой стены.
- **Доска** — площадь, делённая на ширину доски, плюс 5% на раскрой.
- **Кляймеры** — 22 на м².
- **Работы** — «Монтаж фасада из ДПК», 2500 ₽ за м² обшивки.

## Мебель

Единственный расчёт без геометрии: на вход приходят готовые изделия из
каталога и их количество.

```json
{
  "items": {"1964350000": 2, "1964360001": 1}
}
```

Ключ — тот же составной идентификатор, что приходит в выдаче каталога: товар
вместе с кодом конфигурации. Голый `bitrix_id` не подойдёт — разобрать его
однозначно нельзя. Значение — количество. Товар должен быть основным
материалом, иначе 403.

Ответ такой же, как у остальных расчётов. Позиции ключуются тем же составным
идентификатором — ролей, как у объектов с геометрией, у мебели нет. В имени
позиции приходит имя конфигурации, а не базового товара: у разных цветов оно
своё.

```json
{
  "materials": {
    "196435": {
      "productId": 196435,
      "name": "Скамья садовая",
      "ruTag": "Мебель",
      "productUrl": "https://outdoor-mebel.ru",
      "dimension": "шт",
      "pricePerDimension": 12000.0,
      "totalDimensionCount": 2,
      "totalCost": 24000.0
    }
  },
  "works": []
}
```

Работы всегда приходят пустым списком: состав работ по сборке не определён.
Запас 10% к мебели не применяется — сколько изделий выбрали, столько и в смете.

Формат временный: раскрой материала и работы по сборке ещё не решены.

## Грядки

Считаются так же, как мебель, и тем же телом запроса — `items` с составными
идентификаторами конфигураций и количеством:

```json
{
  "items": {"1993400002": 3}
}
```

Размер грядки — это вариант товара, а не параметр расчёта: длину и ширину
выбирают переключателем в каталоге, и в расчёт уходит идентификатор уже
выбранной конфигурации. Цена своего размера приходит вместе с ней, см.
«Цена конфигурации» ниже.

Ответ отличается от мебельного только подписью позиции: `ruTag` приходит
`Грядки`. Работы, как и у мебели, пустые, запас 10% не применяется.

### Цена конфигурации

Цена позиции берётся у выбранной конфигурации, а не у базового товара: две
грядки разной длины — это один товар каталога и две конфигурации, и цена у
каждой своя. Та же цена приходит в поле `prices` выдачи каталога, поэтому
сумма в корзине и сумма в смете сходятся.

Правило общее для всех расчётов, не только для грядок: если у конфигурации
своей цены нет, берётся цена товара из каталога.

## Проект

Несколько объектов одним расчётом. У каждого объекта свой тип, своё имя и то
же тело, что ушло бы в его собственный эндпоинт.

```json
{
  "objects": [
    {
      "type": "terrace",
      "name": "Терраса у входа",
      "vertices": [
        {"x": 0, "y": 0, "vertexType": "house"},
        {"x": 6000, "y": 0, "vertexType": "house"},
        {"x": 6000, "y": 4000, "vertexType": "free"},
        {"x": 0, "y": 4000, "vertexType": "free"}
      ],
      "doorDirection": "N"
    },
    {
      "type": "path",
      "name": "Дорожка к калитке",
      "vertices": [
        {"x": 0, "y": 0, "vertexType": "start"},
        {"x": 1200, "y": 0, "vertexType": "start"},
        {"x": 1200, "y": 5000, "vertexType": "free"},
        {"x": 0, "y": 5000, "vertexType": "free"}
      ]
    }
  ],
  "mergeMaterials": true
}
```

`name` — имя объекта от пользователя. Наружу оно возвращается как есть и
показывается в смете в PDF; на расчёт не влияет.

Имя необязательно: его можно не передавать или прислать пустую строку. Тогда
в ответе придёт `"name": ""`, заголовком раздела в смете станет тип объекта
(«Терраса», «Дорожка»), а в тексте ошибки объект назовётся просто по номеру —
`Объект 2`. Имена не обязаны быть уникальными: одинаковые объекты остаются
отдельными позициями ответа в том порядке, в котором пришли.

`mergeMaterials` определяет форму ответа.

### Материалы объединены

При `"mergeMaterials": true` ответ такой же, как у одиночного расчёта, —
`{materials, works}`. Позиции ключуются **идентификатором товара**, а не
ролью: у террасы и дорожки под одной ролью могут стоять разные товары, а под
разными ролями — один и тот же.

```json
{
  "materials": {
    "196304": {
      "productId": 196304,
      "name": "Террасная доска ДПК",
      "ruTag": "Террасная доска",
      "productUrl": "https://outdoor-mebel.ru",
      "dimension": "м пог",
      "pricePerDimension": 1250.0,
      "totalDimensionCount": 138.0,
      "totalCost": 172500.0
    }
  },
  "works": [
    {
      "name": "Монтаж террасной доски из ДПК",
      "dimension": "м²",
      "pricePerDimension": 1100.0,
      "totalDimensionCount": 37.45,
      "cost": 41195.0
    }
  ]
}
```

Складывается **чистая потребность**, а запас 10% и приведение к единицам
продажи берутся один раз от суммы. Поэтому объединённая смета дешевле, чем
сумма отдельных расчётов тех же объектов: три террасы дают один хвост лаги
вместо трёх. Пересчитать одно из другого нельзя.

Работы объединяются по названию и тарифу: одинаковые складываются в одну
строку, объём и сумма суммируются. Работы с тем же названием, но по разной
цене за единицу, остаются порознь — иначе из строки не было бы видно, по
какой цене посчитано.

### Материалы по объектам

При `"mergeMaterials": false` (или без этого поля) общей сметы нет — ответ
содержит только `objects`, по одному на каждый объект запроса, в том же
порядке. Внутри объекта смета обычная, с ролевыми ключами.

```json
{
  "objects": [
    {
      "type": "terrace",
      "name": "Терраса у входа",
      "materials": {"deckingBoard": {"...": "..."}},
      "works": [{"name": "Монтаж террасной доски из ДПК", "dimension": "м²",
                 "pricePerDimension": 1100.0, "totalDimensionCount": 24.0,
                 "cost": 26400.0}]
    },
    {
      "type": "path",
      "name": "Дорожка к калитке",
      "materials": {"deckingBoard": {"...": "..."}},
      "works": [{"name": "Монтаж дорожки из ДПК", "dimension": "м²",
                 "pricePerDimension": 1100.0, "totalDimensionCount": 13.45,
                 "cost": 14795.0}]
    }
  ]
}
```

Общей стоимости в ответе нет: складывается она на стороне клиента.

### Повторные расчёты

Одинаковый запрос десять минут отдаётся из кеша: тот же ответ и почти без
задержки. Считается по телу запроса целиком, поэтому любое изменение — другая
точка контура, другой товар, другая высота — считается заново. Флаг `debug` в
ключ не входит.

Кеш короткий намеренно: цены и характеристики товаров приезжают синком из
Bitrix, и правка в каталоге должна доходить до сметы за минуты.

## Частота запросов

Адреса API ограничены по частоте, счёт идёт на клиента: у залогиненного по
пользователю, у остальных по адресу.

| Что | Предел |
|---|---|
| Каталог: разделы, товары, конфигурации | 120 запросов в минуту |
| Расчёты, включая проект | 30 в минуту |
| Запуск сборки сметы в PDF | 10 в минуту |
| Опрос готовности и выдача файла | 150 в минуту |

Превышение — **429** с обычным телом ошибки и заголовком `Retry-After`, в
котором число секунд до следующей попытки:

```json
{"error": "Слишком много запросов, попробуйте позже"}
```

Пределы рассчитаны на живого пользователя, который рисует объект и считает
смету. Если фронту нужно больше — скажите, поднимем.

## Ошибки объектов

Ошибка любого объекта роняет весь расчёт — смета проекта без одного из
объектов не смета проекта. К тексту ошибки спереди приписывается, о каком
объекте речь: `Объект 2 «Дорожка к калитке»: Минимум 4 точки`. Статус ответа
тот же, что был бы у одиночного расчёта: 400 у геометрии, 404 у материалов.

Число объектов в проекте не ограничено, но расчёт синхронный: десяток тяжёлых
контуров считается заметное время.

## Смета в PDF

По любому расчёту можно получить смету в PDF. Собирается она фоновой задачей —
расчёт и вёрстка занимают время, — поэтому одним запросом файл не приходит:
задача ставится, потом опрашивается её состояние.

У террасы за таблицами идёт ещё один лист — чертёж подсистемы: лаги, двойные
лаги, поперечины у края, опоры и габаритные размеры, с условными обозначениями
и количествами в штампе. У остальных типов объектов чертежа пока нет, и лист
не добавляется. На состав ответа это не влияет: чертёж живёт только в PDF.

```
POST /api/v1/calculation_report/            запуск
GET  /api/v1/calculation_report/{taskId}/   состояние
GET  /api/v1/calculation_report/file/{name} файл
```

### Запуск

Тело — тип объекта и то же, что уходит в расчёт этого типа:

```json
{
  "type": "terrace",
  "vertices": [
    {"x": 0, "y": 0, "vertexType": "house"},
    {"x": 6000, "y": 0, "vertexType": "house"},
    {"x": 6000, "y": 4000, "vertexType": "free"},
    {"x": 0, "y": 4000, "vertexType": "free"}
  ],
  "doorDirection": "N"
}
```

`type` — `terrace`, `steps`, `fence`, `railing`, `path`, `facade`, `furniture`,
`garden_beds` или `project`. У проекта тело такое же, как у расчёта: `objects` и
`mergeMaterials`. Ответ приходит сразу, со статусом 202:

```json
{"taskId": "11009a94-16aa-4374-96bd-bc401a97c8c8", "status": "pending"}
```

Неизвестный тип объекта и невалидный JSON дают 400. Ошибки геометрии и
подбора товаров на этом шаге не проверяются: расчёт идёт уже в задаче, и они
приходят её состоянием.

### Состояние

```json
{"status": "ready", "url": "/api/v1/calculation_report/file/terrace-b8d391780771.pdf"}
```

| `status` | Что значит |
|---|---|
| `pending` | задача в очереди или считается |
| `ready` | смета готова, рядом `url` файла |
| `failed` | расчёт не прошёл, рядом `error` с текстом |

В `failed` лежит та же ошибка, что вернул бы обычный расчёт — например,
`Ступени вышли бы слишком частыми: ...` или `Нечем закрыть позицию «лага»: ...`,
— так что показывать её можно напрямую.

Опрашивать состояние разумно раз в секунду: смета собирается за несколько
секунд, но задачи выполняются по две за раз и при очереди ждать придётся
дольше.

### Файл

По `url` из готового состояния отдаётся сам PDF, `Content-Type:
application/pdf`. Ссылка постоянная, файл лежит на сервере и повторным
запросом не пересобирается. Имя формируется задачей; чужое или несуществующее
имя даёт 404.

Содержимое сметы: шапка с логотипом, заголовок с типом объекта и датой,
параметры объекта, таблицы материалов и работ с итогами и оговорки о том, что
в расчёт заложено, а что в него не входит.

У проекта смета строится вокруг объектов и показывает их имена. С
объединёнными материалами это перечень «Состав проекта» — имя, тип и
параметры каждого объекта, — а следом общие таблицы материалов и работ. Без
объединения у каждого объекта свой раздел со своей таблицей и итогом, а
внизу — итог по проекту. Оговорки собираются по типам, вошедшим в проект.

## Ошибки

Тело ошибки — `{"error": "текст"}`. Тексты рассчитаны на показ пользователю:
они объясняют, что именно не сошлось, и не содержат внутренних терминов.
В фигурных скобках ниже — подставляемые значения.

### Общие для всех расчётов

| Код | Текст | Когда |
|---|---|---|
| 400 | `Невалидный JSON` | тело запроса не разбирается |
| 404 | `Продукт не найден` | передан идентификатор товара, которого нет в каталоге |
| 404 | `Нечем закрыть позицию «{материал}»: товар не выбран и товара по умолчанию нет` | обязательный материал не задан ни ссылкой, ни товаром по умолчанию |
| 404 | `Не найден товар, выбранный как {материал} (id {id})` | в характеристиках выбранного товара стоит ссылка на несуществующий товар |
| 404 | `У товара {id} ({материал}) не заполнены характеристики` | товар найден, но параметров расчёта у него нет |
| 404 | `У товара {id} не заполнены характеристики, а товара по умолчанию ({материал}) в каталоге нет` | то же про главный материал, когда подставить нечего |
| 500 | `Internal server error` | необработанная ошибка расчёта |

Все 404 про материалы — про наполнение каталога, а не про действия
пользователя: чинятся заведением товара или заполнением его характеристик.

### Терраса

| Текст | Когда |
|---|---|
| `Не переданы точки контура` | `vertices` пустой или отсутствует |
| `Минимум 3 точки` | точек меньше трёх |
| `Направление двери должно быть N, S, E или W` | `doorDirection` задан чем-то другим |

### Ступени

| Текст | Когда |
|---|---|
| `Не переданы точки контура` | `vertices` пустой или отсутствует |
| `Минимум 3 точки` | точек меньше трёх |
| `Не передана высота` | нет `height` |
| `Высота подъёма должна быть больше нуля` | `height` ноль или отрицательная |
| `Есть часть фигуры, не примыкающая к террасе ни одной стороной — ступеням неоткуда начинаться` | нарисованная область не касается террасы; вершины примыкания помечаются `terrace` |
| `Ступени вышли бы слишком частыми: фигуре нужно {n} ступеней, а по высоте {h} мм помещается не больше {k}` | глубина требует больше ступеней, чем позволяет высота: нужно уменьшить глубину или поднять высоту |
| `Ступень выходит шириной {w} мм при минимальной {m} мм: не хватает глубины` | ступеней много, а глубины на них не хватает |
| `Части фигуры пересекаются, и ступени в этом месте не стыкуются: они шли бы в одну сторону с разной шириной` | две области накладываются и требуют разной раскладки в одном месте |
| `Слишком сложная форма: части фигуры пересекаются не углом, ступени в этом месте не состыковать` | области пересекаются не внешним углом — такую форму расчёт не берёт |

Три последние ошибки — про форму: они означают, что фигуру надо перерисовать,
а не поменять параметры.

### Забор

| Текст | Когда |
|---|---|
| `Нужна хотя бы одна линия` | `lines` пустой или отсутствует |
| `Линия {n}: нужно минимум 2 точки` | в линии одна точка |
| `Линия {n}: нулевая длина` | все точки линии совпали |
| `Количество калиток не может быть меньше нуля` | отрицательный `gateCount` |

### Оградка

| Текст | Когда |
|---|---|
| `Нужна хотя бы одна линия` | `lines` пустой или отсутствует |
| `Линия {n}: нужно минимум 2 точки` | в линии одна точка |
| `Линия {n}: нулевая длина` | все точки линии совпали |
| `Линия {n}: примыкание к дому отмечается только на концах линии` | `vertexType: "house"` стоит на внутренней точке |
| `Линия {n}: столбы занимают её целиком, на секции длины не остаётся` | линия короче, чем нужно столбам: ширина секции получилась нулевой |

### Дорожка

| Текст | Когда |
|---|---|
| `Не переданы точки контура` | `vertices` пустой или отсутствует |
| `Минимум 4 точки` | точек меньше четырёх: у дорожки есть стартовая сторона и две боковые |
| `Не отмечена стартовая сторона — с неё начинается дорожка` | ни у одной пары соседних вершин нет `vertexType: "start"` |
| `Стартовая сторона не найдена в контуре` | сторона помечена, но её вершины не совпали с вершинами контура |
| `Форма не похожа на дорожку: {n} вершин в контуре, стороны не сопоставляются попарно` | нечётное число вершин: у боковых сторон разное число поворотов |

### Фасад

| Текст | Когда |
|---|---|
| `Не переданы участки фасада` | `pieces` пустой или не список |
| `Участок {n}: нужен объект со стеной, материалом и точками` | элемент `pieces` не объект |
| `Участок {n}: не указана стена` | нет `wallId` |
| `Участок {n}: минимум 3 точки` | у участка меньше трёх точек |
| `Участок {n}: нулевая площадь` | точки участка лежат на одной прямой |
| `Участки {n} и {m} на стене {стена} накладываются друг на друга` | участки одной стены перекрываются площадью |
| `Направление доски должно быть horizontal или vertical, а не {значение}` | в характеристиках доски неверное `board_direction` |

### Мебель

| Код | Текст | Когда |
|---|---|---|
| 400 | `Нужен словарь id товара и количества` | `items` пустой или не объект |
| 400 | `id и количество должны быть числами` | ключ или значение не приводятся к числу |
| 400 | `Количество для товара {id} должно быть больше нуля` | количество ноль или отрицательное |
| 404 | `Товары не найдены: {id, id}` | перечислены идентификаторы, которых нет в каталоге |
| 403 | `Не основные материалы: {id, id}` | перечислены товары, не помеченные основным материалом |

### Грядки

Те же ошибки и те же статусы, что у мебели: тело запроса и проверки общие.

### Проект

| Текст | Когда |
|---|---|
| `Не переданы объекты проекта` | `objects` пустой или не список |
| `Объект {n}: нужен объект с типом и данными` | элемент `objects` не объект |
| `Объект {n} «{имя}»: неизвестный тип объекта: {тип}` | у объекта нет `type` или он не из списка типов |
| `Объект {n} «{имя}»: {ошибка расчёта}` | объект не посчитался: дальше идёт обычный текст ошибки его типа |

Имя в префиксе появляется, только если оно передано; без него — просто
`Объект {n}`.

Все ошибки в разделах по типам приходят со статусом 400, кроме мебели и
грядок, где статус указан отдельной колонкой, и ошибок объектов проекта, где статус
наследуется от расчёта объекта.

## Отладочный режим

Расчёт помимо сметы строит геометрию: прямоугольники покрытия, лаги, опоры,
полосы ступеней, секции. Наружу она не отдаётся — только смета и работы.

Отладочные страницы получают её, добавляя в тело запроса `"debug": true`:
тогда ответ содержит полный результат расчёта, а смета лежит в нём под ключом
`materials`. Состав отладочных полей у каждого типа свой и контрактом не
является — он может меняться вместе с алгоритмом.

**Флаг работает только для сотрудников.** Отладочные страницы живут за
логином админки, и полный результат приходит лишь тому, кто под ним залогинен.
Запрос снаружи с `"debug": true` ошибки не даёт — приходит обычный ответ со
сметой и работами.

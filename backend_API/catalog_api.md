# API каталога и ресурсный менеджер


Домен: `https://calc.outdoor-mebel.ru` или `https://sollersdev.ru` — API на обоих одинаковый.
Ссылки на текстуры в ответе ведут на тот домен, к которому был запрос.

## Эндпоинты

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/sections/` | плоский список разделов каталога |
| GET | `/api/v1/sections/flat/` | то же самое |
| GET | `/api/v1/sections/tree/` | разделы деревом |
| GET | `/api/v1/products/?<фильтры>` | список товаров, пакетно |
| GET | `/api/v1/products/filters/?tags=<теги>` | какие фильтры есть у категории и их значения |
| GET | `/api/v1/products/<id>/` | одна конфигурация по `id` — тому, что приходит в поле `id` выдачи и в `id` у `ProductResource` |
| POST | `/api/v1/create_project/` | сохранить проект, ответ — код проекта |
| POST | `/api/v1/create_project_test/` | то же, но без писем — для проверок |
| GET | `/api/v1/project/<save_id>/` | сохранённый проект по коду |
| POST | `/api/v1/project/<save_id>/images/` | изображения к заявке — в начало сметы в письме |
| POST | `/api/v1/debug/...` | отладочные копии заявки: без писем, смета файлом, по токену |

Возвращаются только активные и доступные товары.

## Объекты

### Раздел каталога

```json
{
    "bitrix_id": 2314,
    "name": "Террасная доска из ДПК",
    "code": "terrasnaya-doska-iz-dpk",
    "parent_bitrix_id": null,
    "sort": 1
}
```

В дереве у каждого раздела дополнительно есть `children` с такими же объектами.

### Товар

```json
{
    "id": 196435,
    "name": "Универсальная доска AIWOODek 140*18 мм, м.пог",
    "color": "",
    "code": "dpk_doska_universalnaya_holzhof",
    "xml_id": "69083",
    "sort": 1,
    "main_section_id": 2315,
    "sections": [2316, 2995, 2315],
    "preview_text": "",
    "preview_text_type": "html",
    "preview_picture": {
        "id": 524427,
        "url": "https://outdoor-mebel.ru/upload/iblock/...jpg",
        "name": "",
        "type": ""
    },
    "detail_picture": { "...": "то же самое" },
    "glb_file_url": null,
    "texture_urls": {
        "textures_dpc_diffusion": "https://sollersdev.ru/static/DPK/diffusion/....png",
        "textures_dpc_normal": "https://sollersdev.ru/static/DPK/normal/....png",
        "textures_dpc_roughness": "https://sollersdev.ru/static/DPK/roughness/....png"
    },
    "variants_id": [19972101, 19972102],
    "prices": [
        { "price": "364.00", "currency": "RUB" }
    ]
}
```

`variants_id` — другие товары, взаимозаменяемые с этим: тот же товар в другом
цвете или с другой текстурой.

`preview_picture` и `detail_picture` — картинки из Bitrix. Если в Bitrix у
товара заполнена только одна из двух, в обоих полях она. Если своих картинок
у товара нет совсем, отдаётся картинка его предложения: сначала продаваемых
по порядку (первое — предложение по умолчанию), затем остальных.

`color` — легаси-поле, сохраняется для обратной совместимости. Оно лежит вне
характеристик, поэтому параметрическим фильтром не ищется.

## Откуда можно обращаться

Браузеру разрешено читать ответы API с двух адресов: `https://outdoor-mebel.ru`
и `https://micnau.github.io`. С любого другого источника запрос уйдёт, но
браузер не отдаст вам ответ — это CORS, и выглядит он как сетевая ошибка в
консоли.

Локальная разработка фронта (`http://localhost:5173` и подобное) в список не
входит: скажите свой адрес, добавим — он прописывается на сервере, а не в коде.

## Частота запросов

Выдача каталога ограничена 120 запросами в минуту на клиента. Превышение —
429 с телом `{"error": "..."}` и заголовком `Retry-After`. Пределы остальных
адресов описаны в [calculation_api.md](calculation_api.md).

Сохранение проекта и загрузка изображений к нему — 20 запросов в час на
двоих, чтение сохранённого проекта идёт в общий лимит 150 в минуту вместе с
опросом готовности сметы. У отладочных адресов свой лимит — 600 в час.

## Фильтры

Фильтры применяются последовательно: возвращается пересечение по всем выборкам.
**Хотя бы один фильтр обязателен** — запрос без фильтров получает 400.
Неизвестный параметр в строке запроса тоже даёт 400, молча он не игнорируется.

| Параметр | Значение |
|---|---|
| `section_id` | принимается, но выборку не сужает — по договорённости с фронт-командой |
| `ids` | id конфигураций через запятую — те, что приходят в поле `id` |
| `base_ids` | id товаров каталога через запятую, все конфигурации каждого |
| `price_min` | минимальная цена, включительно |
| `price_max` | максимальная цена, включительно |
| `tags` | теги через запятую, см. ниже |
| `properties` | фильтр по характеристикам, JSON-массив предикатов |
| `colors` | цвета через запятую, подходит любой из них, см. «Фильтр по цвету» |
| `sort` | поле сортировки: `sort` (по умолчанию), `id`, `name`, `price` |
| `sort_order` | `ASC` (по умолчанию) или `DESC` |
| `limit` | товаров на странице: от 1 до 500, по умолчанию 50 |
| `page` | страница, по умолчанию 1. Значение больше числа страниц вернёт последнюю |

### Теги

Структура каталога в Bitrix не всегда позволяет отделить нужный товар: в разделе
«Террасная доска из ДПК» лежат и доски, и аксессуары к ним. Теги это обходят.

`walls`, `fences`, `dpk`, `mpk`, `steps`, `furniture`, `garden_beds`,
`fencing`

Тегов можно передать несколько через запятую, и подходит товар с любым из
них: `tags=furniture,garden_beds` вернёт и мебель, и грядки. Пересечения по
тегам не бывает — тег у товара один.

Неизвестный тег даёт 400 со списком непонятых значений — молча он не
отбрасывается, иначе выдача по оставшимся тегам выглядела бы правильной.

Теги `terrasnaya_doska` и `dpk_steps` сняты: они отбирали по названию товара
в обход структуры каталога, а теперь тот же отбор делают `dpk` и `steps`.
Запрос с ними отвечает 400.

### Фильтр по характеристикам

Предикаты едут JSON-ом одним параметром:

```
/api/v1/products/?tags=fences&properties=[{"property":"dimensions.height","op":"eq","value":1800}]
```

- `property` — путь внутри характеристик товара, точка единственный разделитель
- `op` — `eq`, `ne`, `lt`, `lte`, `gt`, `gte`, `in`
- `value` — скаляр, для `in` непустой массив скаляров

Предикаты складываются по И, ИЛИ не поддерживается. JSON выбран из-за типов:
`1800` и `"1800"` в базе разные значения, и число, пришедшее строкой, ничего не
найдёт.

### Фильтр по цвету

Цвет — это поле `color` записи, а не характеристика, поэтому через `properties`
он не ищется и идёт своим параметром. Откуда он берётся: цвет, заданный на
странице материалов у предложения, значения оси или товара; без него — значение
оси цвета Bitrix; без оси — поле товара.

```
/api/v1/products/?tags=dpk&colors=Венге,Тик
```

Названия — те же, что приезжают в `color`, через запятую; подходит товар с
любым из них. Список цветов категории отдаёт `/products/filters/`.

### Какие фильтры есть у категории

```
GET /api/v1/products/filters/?tags=dpk
```

Бек обходит все продаваемые товары (предложения) тегов и отдаёт только те
фильтры, у которых в категории **два значения и больше**: фильтр с одним
значением ничего не отсекает. Значения реальные — то, что встречается у
товаров, с количеством. Считаются они по всей категории, без учёта уже
выбранных фильтров, поэтому список не прыгает при выборе.

`tags` обязателен, других параметров нет; неизвестный тег или параметр — 400.

```json
{
    "tags": ["dpk"],
    "total": 37,
    "filters": [
        {"key": "color", "label": "Цвет", "unit": "", "type": "choice",
         "param": "colors",
         "values": [{"value": "Венге", "label": "Венге", "count": 12},
                    {"value": "Тик", "label": "Тик", "count": 9}]},
        {"key": "price", "label": "Цена", "unit": "₽", "type": "range",
         "params": {"min": "price_min", "max": "price_max"},
         "min": 1200.0, "max": 4300.0},
        {"key": "core_type", "label": "Сечение доски", "unit": "", "type": "choice",
         "param": "properties", "property": "core_type",
         "values": [{"value": "solid", "label": "Полнотелая", "count": 20},
                    {"value": "hollow", "label": "Пустотелая", "count": 17}]},
        {"key": "dimensions.height", "label": "Толщина", "unit": "мм", "type": "choice",
         "param": "properties", "property": "dimensions.height",
         "values": [{"value": 20, "label": "20", "count": 5},
                    {"value": 25, "label": "25", "count": 32}]}
    ]
}
```

- `total` — сколько товаров (конфигураций) в категории.
- `type: "choice"` — список значений. `label` — что показать, `value` — что
  передать. Как применить, говорит `param`:
  - `colors` — выбранные `value` через запятую в параметр `colors`;
  - `properties` — предикат `{"property": <property>, "op": "in", "value": [<value>, ...]}`.
    `value` передаётся как есть, без приведения к строке: `20` и `"20"` разные.
- `type: "range"` — диапазон `min`…`max`; границы передаются параметрами из
  `params`.
- Порядок фильтров: цвет, цена, затем поля категории. Значения с подписями
  идут в заданном порядке, числа — по возрастанию.

Набор полей зависит от тега и от данных: новое поле товара, заполненное
менеджером, появится в списке само, без правки фронта.

У оградки (`tags=fencing`) среди полей есть ширина столба
`components.post.dimensions.width` («Столб: ширина») и тип крышки
`components.post_cap.type` («Крышка-юбка столба: тип крышки»). Их значения —
характеристики самих столба и крышки, ровно те, что приезжают в `properties`
выдачи; применяются они тем же предикатом `properties`.

## Ресурсный менеджер

`ResourceManager.js` берёт на себя сеть, загрузку текстур и кеширование, чтобы не
собирать запросы руками. Написан в асинхронном стиле.

### Перечисления

- `FilterType` — какие бывают фильтры; `COLORS` — массив названий цветов (см. «Фильтр по цвету»)
- `PropertyOp` — операции сравнения для фильтра по характеристикам: `EQ`, `NE`, `LT`, `LTE`, `GT`, `GTE`, `IN`
- `PropertyPath` — согласованные пути до характеристик: `HEIGHT`, `WIDTH`, `LENGTH`, `FENCING_POST_CAP_TYPE`, `FENCING_POST_WIDTH`, `GARDEN_BED_CORNER_BRACKET_TYPE`, `PRICE_CATEGORY`, `CORE_TYPE`, `BOARD_DIRECTION`, `FENCE_TYPE`, `BRAND`
  В `properties` выдачи у любого товара приезжают (если заполнены) габариты `dimensions`, текстуры, `glb_url`, `price_category`, `core_type`, `board_direction`, `fence_type`, бренд `brand`, материал мебели и грядок `material`, связанные товары `related_product_ids` (см. «Связанные товары»), а также `components.post.dimensions`, `components.post_cap.type` и `components.corner_bracket.type`. Размеры столба и тип крышки оградки — характеристики самих столба и крышки, которые стоят в оградке компонентами: путь и значения прежние, но заполняются они у столба и крышки, и у оградки без них этих ключей нет. Значения `components.post_cap.type`: `dpk`, `plastic`, `metal`; `components.corner_bracket.type`: `plastic_joint`, `plastic_angle`, `metal`
- `PriceCategory` — значения ценовой категории: `BUDGET`, `BALANCE`, `PREMIUM` (`budget`, `balance`, `premium`)
- `CoreType` — сечение доски: `SOLID`, `HOLLOW` (`solid` — полнотелая, `hollow` — пустотелая)
- `BoardDirection` — направление фасадной доски на стене: `HORIZONTAL`, `VERTICAL` (`horizontal`, `vertical`)
- `FenceType` — тип забора: `WOVEN`, `BOARD` (`woven` — плетёный, `board` — из доски)
- `SORT_FILEDS` — поля сортировки
- `SORT_ORDER` — порядок сортировки

### Filter

```js
const byPrice = new Filter(FilterType.PRICE_MAX, 1000)
const byName  = new Filter(FilterType.SORT, SORT_FILEDS.NAME)
const byProps = new Filter(FilterType.PROPERTIES, [
    { property: 'dimensions.height', op: PropertyOp.EQ,  value: 1800 },
    { property: 'dimensions.length', op: PropertyOp.LTE, value: 3000 },
])
```

### Ценовая категория

Категория лежит в характеристиках по пути `price_category`, значение одно из
трёх: `budget`, `balance`, `premium`. Значения латиницей — это ключ, а не
подпись: как назвать категорию в интерфейсе, решает фронт.

```js
const budget = new Filter(FilterType.PROPERTIES, [
    { property: PropertyPath.PRICE_CATEGORY, op: PropertyOp.EQ, value: PriceCategory.BUDGET },
])

const notPremium = new Filter(FilterType.PROPERTIES, [
    { property: PropertyPath.PRICE_CATEGORY, op: PropertyOp.IN,
      value: [PriceCategory.BUDGET, PriceCategory.BALANCE] },
])
```

Категория у товара одна, поэтому несколько категорий сразу отбираются `IN`, а
не двумя предикатами: они сложились бы по И и не нашли ничего.

Та же категория приходит в `properties` выдачи, так что подписывать товар
можно тем, что уже приехало, без второго запроса.

### Полнотелая и пустотелая доска

Сечение доски лежит в характеристиках по пути `core_type`, значение `solid`
(полнотелая) или `hollow` (пустотелая). У товаров, где сечение не задано, пути
в `properties` нет вовсе — это «неизвестно», а не «полнотелая».

```js
const hollow = new Filter(FilterType.PROPERTIES, [
    { property: PropertyPath.CORE_TYPE, op: PropertyOp.EQ, value: CoreType.HOLLOW },
])

// Подпись по тому, что уже приехало в выдаче
const coreType = resource.properties[PropertyPath.CORE_TYPE]   // 'solid' | 'hollow' | undefined
const label = { [CoreType.SOLID]: 'Полнотелая', [CoreType.HOLLOW]: 'Пустотелая' }[coreType] ?? ''
```

Фильтр по `core_type` отбирает только товары, у которых сечение заполнено:
доска без него не попадёт ни в `solid`, ни в `hollow`.

### Направление фасадной доски

Как фасадная доска идёт по стене, лежит в характеристиках по пути
`board_direction`, значение `horizontal` (горизонтально) или `vertical`
(вертикально). Это тот же параметр, по которому считается фасад: лаги ложатся
поперёк доски. У товаров, где направление не задано, пути в `properties` нет
вовсе.

```js
const vertical = new Filter(FilterType.PROPERTIES, [
    { property: PropertyPath.BOARD_DIRECTION, op: PropertyOp.EQ, value: BoardDirection.VERTICAL },
])
const { products } = await manager.getResources(new Filter(FilterType.TAGS, ['walls']), vertical)

// Подпись по тому, что уже приехало в выдаче
const direction = resource.properties[PropertyPath.BOARD_DIRECTION]   // 'horizontal' | 'vertical' | undefined
const label = { [BoardDirection.HORIZONTAL]: 'Горизонтально', [BoardDirection.VERTICAL]: 'Вертикально' }[direction] ?? ''
```

Фильтр по `board_direction` отбирает только товары, у которых направление
заполнено: доска без него не попадёт ни в `horizontal`, ни в `vertical`.

### Тип забора

Тип забора лежит в характеристиках по пути `fence_type`, значение `woven`
(плетёный) или `board` (из доски). У товаров, где тип не задан, пути в
`properties` нет вовсе.

```js
const woven = new Filter(FilterType.PROPERTIES, [
    { property: PropertyPath.FENCE_TYPE, op: PropertyOp.EQ, value: FenceType.WOVEN },
])
const { products } = await manager.getResources(new Filter(FilterType.TAGS, ['fences']), woven)

// Подпись по тому, что уже приехало в выдаче
const fenceType = resource.properties[PropertyPath.FENCE_TYPE]   // 'woven' | 'board' | undefined
const label = { [FenceType.WOVEN]: 'Плетёный', [FenceType.BOARD]: 'Из доски' }[fenceType] ?? ''
```

Фильтр по `fence_type` отбирает только товары, у которых тип заполнен:
забор без него не попадёт ни в `woven`, ни в `board`.

### Связанные товары

У террасной доски ДПК (`tags=dpk`), ступеней (`steps`) и оградки (`fencing`) в
`properties` приезжает `related_product_ids` — что предложить вместе с этим
товаром. Ключи всегда одни и те же: `dpk`, `steps`, `fencing`. Значение — число,
id конфигурации в том же виде, что поле `id` выдачи (у предложения — его id):
его можно сразу передать в `getProductById` или в фильтр `PRODUCT_IDS`. Пустая
строка — товар не связан. У товаров, где связанные ещё не заполнялись, пути нет
вовсе.

Раньше здесь было написано, что id — строка, и стенд какое-то время отдавал
строки. Теперь это всегда число, как на боевом.

Связанные задаются у товара и могут быть своими у отдельного предложения,
поэтому у разных предложений одного товара значения бывают разными: например,
к ступени венге — доска и оградка венге, к серой — серые. Читать их нужно у
той конфигурации, которую выбрал пользователь, а не у товара или соседнего
предложения.

```json
"related_product_ids": {
    "dpk": "",
    "steps": 201168,
    "fencing": 201317
}
```

### Проверка фильтров

Фильтры проверяются **до** запроса: кривой предикат падает с сообщением в консоль,
а `getResources` возвращает `null`, не сходив в сеть.

Все предикаты по характеристикам передаются **одним** фильтром `PROPERTIES` с
массивом. Два таких фильтра в одном вызове схлопнутся: последний перетрёт
предыдущий.

Готовые наборы фильтров лежат в `Presets`:

```js
const filters = Presets.terrasnaya_doska_dpk()
```

### ProductResource

```js
this.id                      // id ресурса
this.baseId                  // корневой товар каталога
this.configId                // конфигурация, из которой собран ресурс
this.name
this.code
this.xmlId
this.sort
this.mainSectionId
this.sections                // []
this.previewText
this.previewTextType
this.previewPicture
this.detailPicture
this.prices                  // []
this.properties              // характеристики: путь → значение
this.color                   // цвет: свой со страницы материалов, иначе по оси цвета
this.glbFileUrl              // модель: из характеристик, иначе поле товара
this.productVariants         // id остальных конфигураций того же товара
this.textureUrls             // {textures_dpc_diffusion, textures_dpc_normal, textures_dpc_roughness}
this.textures                // те же ключи, загруженные THREE-текстуры
this.isTextureLoadedSuccessed
```

`id` идентифицирует **конфигурацию**, `baseId` — товар каталога. В `ids` уходит
`id`, в `base_ids` — `baseId`. У торгового предложения `id` — его id в Bitrix,
подробнее в разделе [Торговые предложения](#торговые-предложения).

Текстуры грузятся фоново через `THREE.TextureLoader`, после успеха
`isTextureLoadedSuccessed` становится `true`. При пакетной выдаче загрузка идёт
чанками, поэтому нужная текстура может быть ещё не готова — тогда её можно
дождаться вручную:

```js
await resource.loadTextures(force_reload = false)   // true при успехе, false при ошибке
```

### Методы ResourceManager

```js
await manager.getResources(...filters)
```

Возвращает `{products, total, page, pages, limit}` или `null` при ошибке. Ресурсы
отдаются сразу, не дожидаясь текстур: их загрузка стартует фоном.

```js
await manager.getProductById(productId)   // по id ресурса
await manager.getSections(flat = true)
await manager.getSectionById(id)
await manager.getSectionByName(name)
await manager.getSectionByCode(code)
manager.getCachedProducts()
```

```js
const {filters} = await manager.getFilters(['dpk'])   // какие фильтры есть у категории
const chosen = ResourceManager.filtersFromSelection(filters, {
    color: ['Венге'],
    core_type: ['solid'],
    price: {min: 1500, max: 3000},
})
await manager.getResources(new Filter(FilterType.TAGS, ['dpk']), ...chosen)
```

`filtersFromSelection` превращает выбор по ответу `getFilters` в фильтры
`getResources`: цвета — в `COLORS`, поля характеристик — в один `PROPERTIES` с
предикатами `in`, диапазон цены — в `PRICE_MIN` / `PRICE_MAX`. Ключ выбора —
`key` фильтра, для списка — массив `value`, для диапазона — `{min, max}`.

```js
await manager.saveProject(name, email, data, calculation, images)   // {status, save_id, images}
await manager.uploadProjectImages(saveId, [blob1, blob2])           // {images}
await manager.saveProjectTest(name, email, data, calculation)       // то же, что saveProject, но без писем
await manager.getProject(saveId)              // {save_id, status, data, createdAt}
```

`images` у `saveProject` — сколько изображений будет догружено
`uploadProjectImages`, см. «Изображения к заявке».

Всё, кроме `getCachedProducts`, возвращает `null` при ошибке или если объекта нет.

## Сохранённые проекты

Проект, который нарисовал пользователь, можно сохранить на сервере и потом
открыть по коду.

### Сохранение

`POST /api/v1/create_project/`

```json
{"name": "Иван", "email": "ivan@example.com", "data": {...}, "calculation": {...}, "images": 2}
```

`data` — описание проекта в формате конфигуратора (`PROJECT_FORMAT.md`,
версия 1). Сервер хранит его как есть и не разбирает, но форму проверяет на
входе: подпись `app`, версию, `units`, участок, дом и известные разделы
`elements`; размеры должны быть конечными неотрицательными числами, а
координаты плана — лежать в пределах `plot.sizeMm`. Контуры участков фасада
живут в системе стены, а не участка: там пределов нет вовсе, и отрицательные
координаты проходят. Неизвестное поле или раздел —
отказ: описание принимается целиком или не принимается вовсе, иначе лишнее
поле выглядит учтённым, а на деле теряется. Исключение одно — блок `railing`
у ступеней: его состав в формате не расписан, и внутрь него сервер не
смотрит. Новое поле на фронте — это новая версия формата и правка сервера.

Два послабления против текста спецификации, сделанных по живым заявкам:
`productId` принимается и строкой, и числом, а `railing` у ступеней — и
блоком, и флагом `true`.

Имя и почта в базу не идут: на почту уходит письмо со ссылкой, по которой
проект открывается обратно, а имя подставляется в приветствие. Почта
необязательна — без неё проект сохраняется, письмо просто не уходит.

Оба поля проверяются до сохранения, негодное значение — это 400, и проект
не сохраняется: `name` — строка не длиннее 100 символов, без ссылок
(`http://`, `https://`, `www.`) и переводов строки; `email` — строка с
адресом почты. `null`, пустая строка и отсутствие поля — это «не указано».

`calculation` — необязательные данные для сметы: то же тело, что принимает
`POST /api/v1/calculation_report/`, то есть `type` и всё, что ушло бы в
расчёт этого типа. Прислали — к письму приложится смета в PDF, не прислали —
письмо уйдёт с одной ссылкой на проект. Тело проверяется теми же правилами,
что и сам расчёт: негодное — это 400, и проект не сохранится. Присланное тело
сохраняется вместе с проектом — по нему менеджер видит смету заявки; при
чтении проекта оно не возвращается.

Сама смета собирается уже после ответа, в фоне. Если расчёт на ней упадёт —
скажем, товара не оказалось в зеркале каталога, — письмо всё равно уйдёт,
просто без вложения.

`images` — необязательное число от 0 до 3: сколько изображений фронт
пришлёт к заявке следом, отдельным запросом (см. «Изображения к заявке»
ниже). Они встанут в начало сметы, поэтому ждать их сервер будет, только
если есть `calculation`. Нет поля, `null` или `0` — письма уходят сразу, как
раньше.

По каждой заявке уходит и второе письмо — менеджеру магазина: имя, почта
клиента и две ссылки, на проект и на смету. Его отправка от почты клиента не
зависит: не указал — заявка всё равно дойдёт.

Ответ `201` говорит о сохранении, а не о доставке письма: адрес, на который
письмо не дошло, на код ответа не влияет.

Писем клиентам уходит не больше 5 в час и 20 в сутки на один адрес и не
больше 30 в час на всех. Сверх лимита проект сохраняется и заявка менеджеру
уходит как обычно, письма клиенту просто не будет.

Ответ `201`:

```json
{"status": "pending", "save_id": "wWIxTUyg7jqZuUgZ3kPq9RtLmN0aXbYc", "images": 2}
```

`save_id` — 32 латинские буквы и цифры, по нему проект открывается обратно.
`images` — сколько изображений сервер ждёт к этой заявке: присланное число
или `0`, если ждать незачем (нет `calculation`, письма по заявке не уходят,
сохранение без писем). При `0` изображения не слать — ответ будет 409.
`status` у заявки `pending`: она принята, дальнейшая обработка появится
позже. `test` приходит с отладочного адреса (см. ниже) и в ответ на заявку не
со страницы сайта.

Заявкой считается только сохранение со страницы outdoor-mebel.ru — сервер
смотрит на заголовок `Origin`, который браузер ставит сам. С любого другого
адреса проект сохраняется со статусом `test` и в аналитику не попадает.
С тестового фронта (адрес из списка разрешённых для API) письмо клиенту
уходит как обычно, со сметой, а менеджеру — нет. С неизвестного адреса и
вовсе без `Origin` (скрипт, curl) письма не уходят никому. Расчёты и прочие
запросы с таких адресов работают как обычно, только в аналитике их не видно.

| Код | Когда |
|---|---|
| 400 `{"error": "Нет поля data"}` | нет `data` или `data: null` |
| 400 `{"error": "Неверный формат проекта — ..."}` | описание не прошло проверку; после тире — поле и причина, например `elements.fence.points[0].x: нужно число` |
| 400 `{"error": "Неверный формат проекта — calculation: ..."}` | данные для сметы не прошли проверку расчёта |
| 400 `{"error": "Неверные данные заявки — ..."}` | `name`, `email` или `images` не прошли проверку; после тире — поле и причина, например `email: неверный адрес почты` |
| 400 `{"error": "Невалидный JSON"}` | тело не разбирается как JSON |
| 413 | тело больше 1 МБ; отвечает nginx HTML-страницей, а не JSON |
| 429 | больше 20 сохранений в час, см. `Retry-After` |
| 500 `{"error": "Internal server error"}` | ошибка сервера |

### Сохранение без писем

`POST /api/v1/create_project_test/`

Тот же приём заявки: тело, проверка формата и ответ те же, что у
`create_project`, проект так же сохраняется и открывается по своему коду. Не
делается одно — письма: ни клиенту, ни менеджеру, и смета по `calculation` не
собирается, хотя само поле проверяется. Имя и почта здесь ни на что не
влияют.

Отличается и ответ: `status` у такого проекта — `test`, а не `pending`. Тот
же статус приходит потом при чтении проекта по коду, и по нему в админке
видно, где заявка, а где проверка.

Адрес нужен, чтобы гонять сохранение при отладке, не засыпая почту письмами.
Лимит частоты у него общий с боевым: 20 сохранений в час. Проверить заявку
целиком — с изображениями и сметой — можно отладочными адресами ниже.

### Отладочные адреса

Копии сохранения и загрузки изображений для разработки фронта: весь путь
заявки, но без писем, а смета, которая ушла бы вложением в письме, отдаётся
файлом. Тело и ответы те же, что у боевых адресов, — переключение сменой
префикса на `/api/v1/debug/`.

| Метод | Адрес | Копия чего |
|---|---|---|
| POST | `/api/v1/debug/create_project/` | `create_project/` |
| POST | `/api/v1/debug/project/<save_id>/images/` | `project/<save_id>/images/` |
| POST | `/api/v1/debug/project/<save_id>/report/` | смета из письма, см. ниже |

Каждый запрос — с заголовком `X-Debug-Token: <токен>`. Токен выдаётся
отдельно, в документации его нет. Без заголовка или с чужим токеном — `403
{"error": "Нужен отладочный токен в заголовке X-Debug-Token"}`; если на
сервере отладка выключена — `404`. Сервер разработки фронта должен быть в
списке адресов, которым разрешён API (`CORS_ALLOWED_ORIGINS`), — иначе
браузер ответа не отдаст.

Чем отличаются от боевых:

- проект сохраняется со статусом `test` с любого адреса, писем нет никому;
- обещанные изображения (`images`, только при `calculation`) сервер ждёт
  так же, как у боевой заявки, но без срока в 2 минуты: пока они не
  загружены, их можно прислать;
- работают только с проектами, сохранёнными здесь же: код настоящей заявки
  даёт `404`;
- лимит частоты свой, 600 запросов в час, с боевым не делится.

**Смета.** `POST /api/v1/debug/project/<save_id>/report/` без тела собирает
смету по `calculation` проекта вместе с загруженными изображениями — тот же
PDF, что пришёл бы клиенту в письме. Ответ `202` — как у
`calculation_report/`:

```json
{"taskId": "a1b2c3...", "status": "pending"}
```

Дальше всё как у сметы в PDF: готовность — `GET
/api/v1/calculation_report/{taskId}/`, файл — по `url` из ответа. Звать
можно сколько угодно раз, смета каждый раз собирается заново — например,
после загрузки изображений. У проекта без `calculation` — `409 {"error":
"У проекта нет calculation — смету собирать не из чего"}`.

В `ResourceManager.js` для этого есть `setDebugToken`, `saveProjectDebug`,
`uploadProjectImagesDebug` и `getProjectReportDebug`:

```js
manager.setDebugToken('<токен>');
const saved = await manager.saveProjectDebug(name, email, data, calculation, 2);
await manager.uploadProjectImagesDebug(saved.save_id, [blob1, blob2]);
const pdfUrl = await manager.getProjectReportDebug(saved.save_id);  // адрес PDF или null
```

### Чтение

`GET /api/v1/project/<save_id>/`

```json
{
  "save_id": "wWIxTUyg7jqZuUgZ3kPq9RtLmN0aXbYc",
  "status": "pending",
  "data": {...},
  "createdAt": "2026-09-18T11:50:24+00:00"
}
```

`data` возвращается ровно в том виде, в каком был сохранён; `createdAt` —
время сохранения, ISO 8601 в UTC. Нет такого проекта — `404
{"error": "Проект не найден"}`.

### Изображения к заявке

`POST /api/v1/project/<save_id>/images/`

Изображения (например, виды участка с домом) встают в самое начало сметы в
письме: все вместе на первом листе под заголовком «Визуализация проекта». Одно — на всю ширину, два — друг под другом, три — крупное сверху и два рядом под ним; пропорции сохраняются. Шлются отдельно от заявки, потому что на плохой
сети тяжёлый запрос может не дойти — а заявка должна дойти в любом случае.

Порядок такой:

1. `create_project` с `"images": N` — заявка сохранена, письма ждут.
2. Ответ `201` пришёл — сразу шлём сюда изображения.
3. Письма уходят, как только изображения приняты (в пределах 10 секунд), или
   через **2 минуты** после заявки — без изображений, если они так и не
   дошли.

Тело — `multipart/form-data`, файлы в поле `images`, по порядку листов:

```js
const form = new FormData();
form.append('images', blob1, 'view1.jpg');
form.append('images', blob2, 'view2.jpg');
fetch(`/api/v1/project/${saveId}/images/`, {method: 'POST', body: form});
```

Файлы — JPEG, PNG или WEBP, каждый до 5 МБ, не больше обещанного в заявке
числа (меньше можно). Сервер пересохраняет их в JPEG с длинной стороной до
2000 точек, так что слать крупнее незачем. Лучше заранее ужать снимок
(`canvas.toBlob(cb, 'image/jpeg', 0.85)`, ~1600 точек по длинной стороне):
на плохой сети это решает больше всего.

Изображения принимаются **один раз** и только пока заявка их ждёт. Если
запрос упал по сети, его можно повторить — пока не вышли 2 минуты. Ответ
409 значит «больше не ждём»: изображения уже приняты (например, первый
запрос всё-таки дошёл) или письмо ушло без них. Повторять после 409 нечего.

Ответ `201`:

```json
{"images": 2}
```

| Код | Когда |
|---|---|
| 400 `{"error": "Нет файлов в поле images"}` | в запросе нет файлов |
| 400 `{"error": "Изображений больше, чем обещано в заявке: N"}` | файлов больше, чем `images` в заявке |
| 400 `{"error": "Неверное изображение — ..."}` | файл не годится; после тире — какой и почему, например `images[1]: файл больше 5 МБ`. Ничего не сохранено, можно прислать заново |
| 404 `{"error": "Проект не найден"}` | нет заявки с таким кодом |
| 409 `{"error": "Изображения к этой заявке не ждём"}` | заявка изображений не обещала, они уже приняты или письмо ушло |
| 413 | тело больше 20 МБ; отвечает nginx HTML-страницей, а не JSON |
| 429 | лимит общий с сохранением: 20 запросов в час, см. `Retry-After` |
| 500 `{"error": "Internal server error"}` | ошибка сервера |

## Конфигурации

`GET /api/v1/products/` отдаёт **конфигурации** товара. Конверт и форма записи
прежние, `ProductResource` собирается из них без единой правки — на стороне
фронта менять ничего не нужно.

Тот же ответ доступен и по адресу `/api/v1/configured_products/`.

Конфигурация — это торговое предложение (у товара с вариантами по записи на
каждое продаваемое, со своими id, именем, ценой, текстурами и моделью) либо
сам товар без вариантов — одна запись. Форма записи одна и та же, поэтому
разбирать два разных случая не нужно.

| Поле | Откуда берётся |
|---|---|
| `id` | id предложения в Bitrix; у товара без вариантов — id самого товара, то же, что `base_id` |
| `base_id` | товар каталога, его же ждёт фильтр `base_ids` |
| `config_id` | `id` строкой |
| `name` | имя для калькулятора, если задано; иначе у предложения — его имя из Bitrix, у товара — имя товара |
| `color` | цвет, заданный на странице материалов (у предложения, значения оси или товара); без него — имя значения оси цвета; без оси — поле товара |
| `preview_picture` | сначала превью, заданные на странице материалов: у предложения, у значения оси, у товара; затем картинки Bitrix: предложения, товара — первое, что есть. У каждой строки сначала превью, без него — детальная картинка; у товара без своих картинок — картинка его предложения, как в `preview_picture` товара выше |
| `detail_picture` | так же, как `preview_picture`, но из картинок Bitrix у каждой строки сначала детальная, без неё — превью |
| `glb_file_url` | `glb_url` из характеристик, иначе поле товара; полная ссылка |
| `texture_urls` | `textures.diffusion_url`, `textures.normal_url`, `textures.roughness_url`; полные ссылки |
| `discontinued` | `true` у предложения, снятого с продажи; в списках всегда `false` |
| `variants_id` | остальные конфигурации того же товара |
| `properties` | только публичные характеристики |
| `prices` | у предложения — его цена из Bitrix; у товара без вариантов — своя, если задана на нашей стороне, иначе цена товара из Bitrix |

В `properties` приезжают не все характеристики, а публичные: габариты
(`dimensions`), текстуры (`textures`), модель (`glb_url`), ценовая категория
(`price_category`), сечение доски (`core_type`), направление фасадной
доски (`board_direction`), тип забора (`fence_type`), бренд (`brand`),
материал мебели и грядок (`material`), связанные товары
(`related_product_ids`) и тип уголка грядки (`components.corner_bracket.type`).
У оградки к ним добавляются характеристики её столба и крышки
(`components.post.dimensions`, `components.post_cap.type`), у забора — модель
калитки (`wicket_glb_url`, см. ниже). Товар может показать что-то сверх
этого, и тогда оно приедет **вместе** с перечисленным, а не вместо него.
Остальное — роли, ссылки на компоненты, нормы расхода — кухня расчёта и
наружу не идёт.

У забора в `properties` приезжает модель калитки — `wicket_glb_url`, полная
ссылка. Это модель той калитки, что войдёт в расчёт забора: загружают её у
товара-калитки, а не у каждого забора. Если у калитки модели нет, приходит
то, что вписано у самого забора, а если нет и его — ключа нет.

`prices` у конфигураций одного товара могут отличаться: у грядки на два метра
своя цена, у метровой своя, хотя товар каталога у них общий, — это разные
предложения. Список остаётся списком прежней формы — подменяется только
сумма, валюта берётся из прайса.

Фильтры `price_min` и `price_max` отбирают **конфигурации** по их собственной
цене — той же, что приходит в `prices`: у предложения его цена, у товара без
вариантов — своя, если задана, иначе цена товара. Из товара приезжают только
те конфигурации, что прошли фильтр. У товара с торговыми предложениями своей
цены в Bitrix нет, поэтому отбирать его по цене товара было бы нечем.
Конфигурация без цены фильтр по цене не проходит. Граница — конечное число:
на `nan`, `inf` и нечисловое значение ответ 400.

`variants_id` считается **до** фильтра по характеристикам: переключиться на
другой цвет можно всегда, даже когда выборка сужена.

`preview_text` — описание для калькулятора у предложения, иначе у значения
оси, иначе у товара, а если нигде его нет — анонс товара из Bitrix
(`preview_text_type` у заданного на странице материалов — `text`). Имя,
описание и превью для калькулятора заводят на странице материалов, когда
показать нужно не то, что в Bitrix.

Всё в конфигурации решается одним правилом: своё у варианта (предложения),
иначе у значения оси, иначе у товара. Если одно и то же задают значения
нескольких осей, берётся первая ось по приоритету.

У предложения могут быть свои характеристики — текстуры, модель, габариты и
другие параметры: их заводят на странице материалов. Чего у предложения нет,
приезжает от товара и выбранных значений осей. Загруженные файлы
лежат на сервере API, и ссылки на них приходят полными, от домена, на
который пришёл запрос (`https://calc.outdoor-mebel.ru/media/…`); ссылки,
вписанные вручную, приходят как есть.

Товар целиком тоже могут скрыть у нас: тогда он вместе со всеми
предложениями пропадает из каталога (списки, `/products/<id>/`, конфигурации),
а расчёт по его id — старые сохранения — работает как прежде.

Значение оси могут выключить у нас: тогда все предложения с ним пропадают из
выдачи и из `variants_id`. Так же можно выключить и одно
предложение. Предложение, выключенное так, по своему id по-прежнему
находится (`/products/<id>/`) — его хранят старые сохранения, — и приходит с
`discontinued: true`, а в смете помечается «снято с продажи». Id остальных
предложений от этого не меняются.

### Фильтры этого адреса

`base_ids`, `ids`, `tags`, `price_min`, `price_max`, `properties`, `colors`, `sort`,
`sort_order`, `limit`, `page`. Неизвестный параметр — 400, как и в каталоге.

`ids` здесь принимает **id конфигурации** — тот, что приходит в поле `id`, — а
`base_ids` — id товара каталога. Разбирает id сервер, фронту про устройство
знать не нужно.

Сортировка идёт по конфигурациям, а не по товарам: `name` — имя
конфигурации, `price` — цена конфигурации (у предложения его цена, у товара
без вариантов своя, если задана, иначе цена товара), `id` — id
конфигурации. `sort` — порядок товаров в каталоге, а внутри товара —
порядок его конфигураций: у предложений это их сортировка в Bitrix.

`section_id` принимается, но выборку не сужает — как и раньше.

`id` конфигурации можно сохранять в проекте и слать в расчёт. У предложения
это его id в Bitrix, у товара без вариантов — id самого товара. Id товара,
который продаётся предложениями, конфигурацией не является: в `ids`,
`/products/<id>/` и расчёт идёт id предложения, а для выборки по товару есть
`base_ids`.

**Изменение формата (#134).** Раньше id товара без вариантов приходил с
приписанным `0000` (`1964350000` вместо `196435`), и `config_id` у него был
`"0000"`. Теперь `id` — сам id товара, `config_id` — он же строкой. Старые
id с `0000` сервер больше не находит: кеши со старыми id нужно сбросить, а
сохранённые с ними проекты откроются без этих товаров.

### Торговые предложения

У товара, который в Bitrix продаётся торговыми предложениями, конфигурации — это
его предложения: по одной записи на каждое продаваемое. Сочетаний осей,
которых нет в продаже, в выдаче нет.

- `id` записи — id предложения в Bitrix, например `199761`. Он долговременный:
  его можно сохранять в проекте и слать в расчёт, как любой другой `id`.
- Цена и картинки — собственные у предложения. Характеристики — товара, с
  патчами вариантов предложения, как и у других конфигураций.
- `variants_id` — остальные продаваемые предложения того же товара.

Как находятся id, пришедшие в `ids`, `/products/<id>/` и расчёт:

- сначала id ищется как предложение — в том числе снятое с продажи: оно
  находится, `/products/<id>/` отдаёт его с `discontinued: true`, а в смете
  позиция подписывается «(снято с продажи)». В списки и в `variants_id` такое
  предложение не попадает, поэтому там `discontinued` всегда `false`;
- не нашлось — id ищется как товар без вариантов; id товара с
  предложениями не находится.
